Phone and voice control

There are two ways to control a board from a phone web page, and you can also use the Telegram bot at the end of this section. To see several values on a phone at once, or control the board with switches and sliders, see the Phone dashboard.

Voice control steps

  1. Choose the example "Voice-controlled LED (MQTT)", fill in your Wi-Fi name and password, and press "Upload and run".
  2. When the monitor shows "Connected to the MQTT broker", note the MQTT topic name.
  3. Open the voice control page, enter the topic name and press "Connect".
  4. Press the voice button, allow the microphone, and say "on", "off" or "blink". A sentence such as "turn the light on" also works.

If voice does not work, press the On and Off buttons, or use your phone keyboard's microphone in the text command box. On Windows you can also press Win + H for voice typing.

Topic names and MQTT topics: the name you enter makes up two topics. With led-1, commands use esp32-mp-class/led-1/command and board reports use esp32-mp-class/led-1/state. Other MQTT tools can subscribe or publish to them too.

Using your own MQTT broker: open "Advanced" on the voice control page and fill in the broker address, WSS port, path, username and password. Change BROKER, MQTT_PORT, MQTT_USER and MQTT_PASSWORD in the program to the same broker. The voice control page does not save the password, so enter it again after reloading. The board uses unencrypted port 1883 by default, so others on the network may see the login. Use a password made only for this broker.

Telegram bot

  1. Search for @BotFather on Telegram, send /newbot, and follow the steps to name your bot. You will get a bot token.
  2. Choose the example "Telegram bot LED", fill in your Wi-Fi name, password and BOT_TOKEN, and press "Upload and run".
  3. Send your bot any message, and the monitor shows your CHAT_ID. Put the number in the program and upload again.
  4. Send /on, /off or /status to control the LED. Pressing the button sends a notification to your phone.

The board checks for new messages about every 2 seconds, so replies can take a few seconds. Only the chat set in CHAT_ID can control the board, and old commands from before it started are not run. If your school network blocks Telegram, try a phone hotspot.

Wi-Fi is 2.4GHz only. The ESP32 cannot connect to 5GHz networks.

Once you have typed a Wi-Fi name and password, the site remembers the last ones and fills them into the next examples you load, so you need not type them again. To use another Wi-Fi, change SSID and PASSWORD in the program.

Phone dashboard

The phone dashboard shows sensor readings on a phone, and lets you control the board with switches, buttons and sliders. The board's program decides what is on the screen: when the program says board.gauge("Temperature"), a temperature gauge appears on the phone, with nothing to set up there. The data passes through an MQTT broker, so the board and the phone do not have to share a Wi-Fi network, but both need the internet. Examples 27–38 all use the phone dashboard.

Steps

  1. Choose the example "27. Dashboard basics: LED switch and button", fill in the Wi-Fi name and password, and press "Upload and run".
  2. The site first saves the dashboard helper dash.py to the board's /lib, and the monitor says "Saved the phone dashboard helper dash.py to the board's /lib". When the board already has the same version, this is skipped, so uploads stay fast.
  3. Once the board reaches the MQTT broker, the dashboard's address and a QR code appear above the monitor. Scan it with a phone camera to open the phone dashboard page with the topic name already filled in.
  4. You can also open the phone dashboard page yourself (there is a link in "Settings and help"), enter the topic name shown in the monitor, and press "Connect".

Widgets

First create the dashboard with board = dash.Dashboard(TOPIC_NAME, SSID, PASSWORD), then the widgets, and finally call board.start() to connect. Call board.check() every time round the loop: it reads the phone, sends new values, and reconnects if the connection drops.

No need to worry about sending too fast: each widget sends at most every 0.5 seconds, so calling .set() all the time in the loop does not flood the public broker, and the phone always shows the newest value. The broker keeps the values of switches, sliders and number settings, so after a restart the board goes back to their last state. A dashboard holds up to 30 widgets.

Safety of the direction pad, joystick and tilt: while a key or the joystick is held, the phone sends again every 0.4 seconds; while tilt is on, it sends every 0.2 seconds. If the board hears nothing for more than 1 second, or loses the connection, the direction pad's .value goes back to "" and the joystick's and tilt's .x and .y go back to 0 by themselves. Switching to another app releases them too. So a car stops if the phone freezes, runs flat or leaves the Wi-Fi. For the first test, lift the car so its wheels are off the ground.

Phone tilt: phones only share the tilt sensor with pages opened from https addresses, so use the live site or the address the QR code opens. The first time "Start tilt control" is pressed, an iPhone asks whether the page may use motion sensors; choose "Allow". Flat on a table is 0, and 45 degrees is full. Hold the phone upright; held sideways, left-right and back-forward swap. Computers usually have no tilt sensor.

Logs: a log lives only on the phone page and only collects rows while the page is open, keeping the newest 1000 (about 83 minutes at one row every 5 seconds). When it is full, the count turns red and the oldest rows are dropped. Reloading or closing the page clears it, so press "Download CSV" first. The CSV's first two columns are the date and the time (to the second) the phone got each row, and Excel and Google Sheets open it directly. For long recordings without keeping the phone open, use Google Sheets.

Board info: below "Board: online", the phone dashboard shows the board's Wi-Fi signal, running time and free memory, updated every 10 seconds, with no code needed. A signal of -60 dBm or more is strong and below -70 dBm is weak, when controls may lag. Free memory that keeps falling means something in the program keeps piling up. The board's IP address is never sent.

Alert sound: browsers only let a page make sounds after it has been tapped, so the alert card on the phone dashboard has a "Turn on alert sound" button; tap it after opening the page. Alerts are not kept by the broker, so a phone opened later does not get earlier alerts.

Asking Gemini for a dashboard program: "Write a phone dashboard program" in the "Gemini prompts" menu includes how to use every widget; see Gemini prompts.

Topic names and MQTT topics: for the topic name dash-1, everything is under esp32-mp-class/dash-1/dash/: layout lists the widgets, state says whether the board is online, info holds the board info, out/… holds the board's values and in/… what was done on the phone.

Using your own MQTT broker: fill in the broker under "Advanced" on the phone dashboard page, and change the program to dash.Dashboard(TOPIC_NAME, SSID, PASSWORD, broker="broker address", port=1883, user="username", mqtt_password="password").

About dash.py: do not edit /lib/dash.py on the board, because the site puts its own version back at the next upload. When you upload without this site (with Thonny, for example), open /lib in Board files to download dash.py, then put it on the other board. The phone dashboard page does not need Web Serial, so it opens in phone and computer browsers, but it has not been tested on every kind of phone.

When the board cannot connect: if the school firewall blocks port 1883, the monitor keeps saying "Could not connect, retrying in 5 s"; try a phone hotspot instead. When the phone dashboard page says the board is offline or not responding, check that the program on the board is running and that both sides use the same topic name.

Saving sensor data to Google Sheets

The example "Log DHT11 data to Google Sheets" adds a row of date, time, temperature and humidity every minute. Google Apps Script is free, but needs setting up once.

  1. Create a new Google Sheet, and enter the headings in A1 to D1: Date, Time, Temperature, Humidity. Keeping the date and the time in separate columns shows the time to the second.
  2. Choose "Extensions" → "Apps Script", replace the contents with the program below, and save: 
    function doGet(e) {
  var temp = Number(e.parameter.temp);
  var hum = Number(e.parameter.hum);
  if (isNaN(temp) || isNaN(hum)) {
    return ContentService.createTextOutput("bad data");
  }
  var book = SpreadsheetApp.getActiveSpreadsheet();
  var zone = book.getSpreadsheetTimeZone();
  var now = new Date();
  book.getSheets()[0].appendRow([
    Utilities.formatDate(now, zone, "yyyy-MM-dd"),
    Utilities.formatDate(now, zone, "HH:mm:ss"),
    temp,
    hum
  ]);
  return ContentService.createTextOutput("ok");
}
  3. Choose "Deploy" → "New deployment", with the type "Web app". Set "Execute as" to "Me" and "Who has access" to "Anyone", then complete the authorization.
  4. Copy the deployment URL, which ends in /exec. First test it in a browser by adding ?temp=25&hum=60 to the end. If the page shows ok and the sheet gains a row, the setup is correct. You can delete that row afterwards.
  5. Choose the example "Log DHT11 data to Google Sheets", fill in your Wi-Fi name, password and SCRIPT_URL, and press "Upload and run". Reaching Google takes a few seconds each time, so the rows are a few seconds further apart than SEND_SECONDS.

Anyone with the URL can write to the sheet. Do not project or share it. If it leaks, archive the deployment under "Deploy" → "Manage deployments" and create a new one.

School Google accounts may not allow access for "Anyone". If so, use a personal account. After changing the Apps Script later, edit the deployment in "Manage deployments" and publish a new version for the change to take effect.
